# Data Schemas

**Scope:** this file covers the data model, validation rules and business rules. The system enforces all of them (API and database), whatever client is used.
How fields are masked, formatted, defaulted or entered in forms is described in `be-rich-ui/specs/ui-behavior.md` (UI repository).

---

## 1. Conventions

- **Naming:** field names use `snake_case`.
- **Identifiers:** every `id` is a UUID v4 generated by the server.
- **Timestamps** (`created_at`, `updated_at`): ISO 8601 in UTC, set by the server, read-only.
- **Calendar dates** (`date`): ISO 8601 `YYYY-MM-DD` with no time part, interpreted in the `America/Sao_Paulo` timezone. "Today" means today in that timezone.
- **Money:** `decimal(12,2)`, or integer cents in storage. **Never floating point.** Entry amounts are always positive. The entity (Expense or Income) decides the direction. Account balances can be negative.
- **Default currency:** every total, dashboard, projection and balance is shown in the household's `default_currency` (§4). Conversion rules are in §16.
- **Formatted values** (CPF, CEP, phone): stored **normalized** (digits only, or E.164). Formatting is a presentation concern.
- **Text:** leading and trailing whitespace is trimmed before validation. An empty string counts as "not provided".
- **Uniqueness by name:** when a name must be unique, the comparison ignores case.
- **Month arithmetic:** adding N months keeps the day of month, clamped to the last day of the target month (2026-01-31 + 1 month = 2026-02-28). Applying a day-of-month setting (1–31) to a shorter month uses the same clamp.
- **Series dates are computed from the anchor:** every date in a series (installments or recurrences) is computed from the series' first date (the anchor), **never** from the previous item. Clamps therefore never pile up: day 31 gives Jan 31 → Feb 28 → **Mar 31**.
- **Business-day adjustment:** some computed dates are moved to the next business day (§17). The adjustment is always the **last** step, applied to each date on its own, and it never changes the anchor.
- **Required column:** `Yes`, `No`, or `Cond.` (conditional; the condition is described in the field's notes or in the rules).

## 2. Entity overview

```
Household ─┬─< User
           ├─< Invitation
           ├─< Account             (type: BANK | CASH)
           ├─< Card >── Account (paying account)
           ├─< Category            (type: EXPENSE | INCOME)
           ├─< Recurrence >── User, Account, Card (optional), Category
           ├─< Expense >── User (spender), Account, Card (optional), Category, Recurrence (optional)
           └─< Income  >── User (receiver), Account, Category, Recurrence (optional)

System-wide (not owned by a household): ExchangeRate, Holiday
Auth-only (defined in auth.md): Session, PasswordResetToken
```

Every household-owned record belongs to exactly one household. A user can only read and write data from their own **current** household. A new reference to a record in another household is rejected. Existing references to former members are the exception (§4.2).

## 4. Household

The group of people who share finances. It is created automatically when someone signs up **without** an invitation, and also for a member who leaves or is removed (§4.2). **Every member has the same permissions:** they can see, create, edit and delete all of the household's data, invite new members, and remove members.

| Field | Type | Req. | Default | Constraints / notes |
|---|---|---|---|---|
| `id` | uuid | Yes | auto | |
| `name` | string(1–60) | Yes | `"<first name>'s household"` | |
| `default_currency` | Currency | Yes | `BRL` | The currency used for every calculation and display, and the default currency for new entries and accounts. Any member can change it. Changing it **does not modify stored data**, because all conversions are calculated when needed (§16). |
| `created_at` | timestamp | Yes | auto | |
| `updated_at` | timestamp | Yes | auto | |

### 4.1 What a new household starts with

- The default expense and income categories (§9).
- One `CASH` account named "Cash" ("Dinheiro" in Portuguese), with an opening balance of 0 (§7).
- The name "<first name>'s household" ("Casa de <first name>" in Portuguese).

All of these use the creating user's `language` (§5). Afterwards they are ordinary data that the household can rename.

### 4.2 Leaving or being removed

1. A member can **leave** the household, and any member can **remove** another member.
2. The **last** member of a household cannot leave it or be removed.
3. The departing user **keeps their account** and is moved to a **new, empty household** of their own (set up as in §4.1). Their access to the old household ends immediately, including any active sessions.
4. **All data stays in the old household:** entries, recurrences, cards and accounts. References to the departing user (`spender_id`, `receiver_id`, `person_id`, `owner_id`, `created_by_id`) are **kept** and displayed as "Name (former member)".
5. **Cards** owned by the departing user are **archived** automatically. A card can be reactivated by assigning a current member as its owner.
6. **Recurrences** with `person_id` set to the departing user keep projecting. To register one of their occurrences, the person must first be changed to a current member.
7. **Pickers** only list current members. Updating a row that already references a former member is allowed as long as that reference isn't changed. Any **new** reference must point to a current member.
8. **Invitations** sent by the departing user stay valid.
9. A former member cannot be invited again in v1, because their email already has an account (§6.1 rule 6).

## 6. Invitation

An invitation to join a household. It is delivered as a link sent by email.

| Field | Type | Req. | Default | Constraints / notes |
|---|---|---|---|---|
| `id` | uuid | Yes | auto | |
| `household_id` | uuid → Household | Yes | | The inviter's household. |
| `email` | string(≤254) | Yes | | The invited address, stored lowercase. |
| `token_hash` | string | Yes | | Hash of the token in the link. The raw token is only ever sent in the email and is never stored. |
| `invited_by_id` | uuid → User | Yes | current user | |
| `status` | InvitationStatus | Yes | `PENDING` | |
| `expires_at` | timestamp | Yes | `created_at + 7 days` | |
| `accepted_at` | timestamp | No | | Set when the invitation is accepted. |
| `created_at` | timestamp | Yes | auto | |

### 6.1 Rules

1. Any household member can invite someone, revoke a pending invitation, or resend one.
2. The token is random (at least 128 bits) and can be used **once**. The link has the form `<app-url>/invite/<token>`.
3. Each email can have **only one** `PENDING` invitation per household. Resending revokes the current invitation (`REVOKED`) and creates a new one with a new token and a new expiry date.
4. An invitation is treated as `EXPIRED` once `now > expires_at`. The status can be computed when it is read or updated by a scheduled job.
5. **Accepting** an invitation (only valid while `PENDING` and not expired):
   - opens the signup form with the email **pre-filled and locked**;
   - creates the User inside the invitation's household;
   - sets the invitation to `ACCEPTED` with `accepted_at = now`.
6. **Inviting an email that already has an account is rejected** with "This email already has an account". Moving an existing account between households is out of scope for v1 (§19).
7. Invitation endpoints never reveal whether an email is registered anywhere other than the inviter's own household (to prevent account enumeration). The one exception is the error in rule 6, which is only shown to authenticated members.

## 10. Expense

Each Expense row is **one payment, made with one payment method from one account, that affects cash flow on one date**. A single purchase can produce several rows:

- **Installments:** N rows linked by `installment_group_id` (§10.1).
- **Split payment** (one purchase paid with more than one method): one set of rows per method, linked by `split_group_id` (§10.5).
- **A registered occurrence of a fixed expense:** a row linked to a Recurrence (§12).

| Field | Type | Req. | Default | Constraints / notes |
|---|---|---|---|---|
| `id` | uuid | Yes | auto | |
| `household_id` | uuid → Household | Yes | | |
| `spender_id` | uuid → User | Yes | current user | Who made the expense. Must be a current member (§4.2 rule 7). |
| `transaction_date` | date | Yes | today | The date the purchase happened. |
| `payment_date` | date | Yes | derived | The date the money leaves the account. Computed by the server (§10.2 and §10.3) and **not accepted from the client**. |
| `amount` | decimal(12,2) | Yes | | Greater than 0, in `currency`. This is the amount of **this row**, which for a series means a single installment. |
| `currency` | Currency | Yes | household `default_currency` | The original currency. It is never overwritten by conversion. |
| `payment_method` | PaymentMethod | Yes | | |
| `card_id` | uuid → Card | Cond. | | Required when `payment_method` is `CREDIT` or `DEBIT`, and must be null otherwise. The card must be active, and its `type` must support the method. |
| `account_id` | uuid → Account | Yes | see notes | The account the money leaves. It must be active. **For `CREDIT` and `DEBIT`** the server sets it to `card.account_id` and ignores any value from the client. **For `CASH`** it must be a `CASH` account, and defaults to the household's first one. **For `PIX`, `BOLETO` and `BANK_TRANSFER`** it must be a `BANK` account. |
| `category_id` | uuid → Category | Yes | | Must be an active category with `type = EXPENSE`. |
| `description` | string(≤200) | No | | |
| `installment_number` | integer | Yes | `1` | From 1 to `installment_total`. |
| `installment_total` | integer(1–60) | Yes | `1` | |
| `installment_group_id` | uuid | Cond. | | Shared by every row in an installment series. Null when `installment_total = 1`. |
| `split_group_id` | uuid | No | | Shared by every row of a split-payment purchase. Null for a purchase paid with a single method. |
| `recurrence_id` | uuid → Recurrence | No | | Set when this row is a registered occurrence of a fixed expense (§12). The Recurrence must have `type = EXPENSE`. |
| `occurrence_date` | date | Cond. | | Required when `recurrence_id` is set, and must be null otherwise. Identifies which occurrence this row registers. (`recurrence_id`, `occurrence_date`) is **unique**. |
| `created_by_id` | uuid → User | Yes | current user | Who entered the record, which can differ from `spender_id`. Read-only. |
| `created_at` | timestamp | Yes | auto | |
| `updated_at` | timestamp | Yes | auto | |

### 10.1 Creating installments

1. The client sends the **total** purchase amount and the number of installments, N (default 1).
2. The server creates N rows that share a new `installment_group_id`, with `installment_number` from 1 to N.
3. **Amounts:** each row gets the total divided by N, rounded **down** to the cent. The remaining cents are added to **installment 1**. The sum of the rows always equals the total.
   Example: R$ 100.00 in 3 installments gives 33.34, 33.33, 33.33.
4. **Dates:** installment *i* has its nominal date at `anchor + (i − 1) months` (see Conventions). The anchor is the first nominal date from §10.2. For credit series, each installment uses the card's `due_day` clamped to its own month. The business-day adjustment (§17) is applied afterwards, where the method calls for it.
5. When `payment_method = DEBIT`, `installment_total` must be 1.
6. A row with `recurrence_id` set must have `installment_total = 1`.

### 10.2 Payment date

| Payment method | `payment_date` of the first row (the anchor) | Business-day adjustment |
|---|---|---|
| `CASH`, `PIX`, `DEBIT`, `BOLETO`, `BANK_TRANSFER` | `transaction_date` | No. It is the date the user actually paid. |
| `CREDIT` | The due date of the card statement that the purchase belongs to (algorithm in §10.3). | **Yes** (§17) |

### 10.3 Credit statement algorithm

Inputs: the purchase date `d`, plus the card's `best_buy_day` (B) and `due_day` (D). Both B and D are clamped to the length of the month they are applied to.

1. **Closing month:** if `d.day < B`, the purchase belongs to the statement that closes in `d`'s own month. Otherwise (`d.day ≥ B`) it belongs to the statement that closes the following month. A purchase made **on** the best buy day therefore goes to the next statement.
2. **Nominal due date:** if `D > B`, the statement is due on day D of the closing month. Otherwise (`D ≤ B`) it is due on day D of the month after the closing month.
3. **Business-day adjustment:** if the nominal due date is not a business day, it moves to the next business day (§17).

Examples (before adjustment unless noted):

| Card (B / D) | Purchase | Statement closes | `payment_date` |
|---|---|---|---|
| 25 / 5 | 2026-11-10 | Nov 25 | **2026-12-07** (Dec 5 is a Saturday, so it moves to Monday) |
| 25 / 5 | 2026-11-25 | Dec 25 | **2027-01-05** |
| 25 / 5 | 2026-12-02 | Dec 25 | **2027-01-05** |
| 3 / 10 | 2026-11-01 | Nov 3 | **2026-11-10** |
| 3 / 10 | 2026-11-05 | Dec 3 | **2026-12-10** |

### 10.4 Card changes do not affect existing records

Changing a card's `best_buy_day`, `due_day` or `account_id` affects **new** records and **projected** recurrence occurrences only. The `payment_date` and `account_id` stored on existing rows are never recalculated.

### 10.5 Split payments

This rule applies when a single purchase is paid with more than one method (for example, part Pix and part credit in 3 installments):

- One set of rows is created per method, and every row shares a new `split_group_id`. Each method can have its own installments, so it can have its own `installment_group_id`.
- All rows in a split group must share the same `transaction_date`, `spender_id`, `currency`, `category_id` and `description`.
- The client sends the total plus a list of parts (`payment_method`, `card_id` or `account_id`, `amount`, `installments`). The part amounts must add up to the total.
- A purchase paid with a single method has a null `split_group_id`.
- Rows with `recurrence_id` set cannot belong to a split group.

### 10.6 Editing and deleting rows in a series

Updating or deleting a row whose `installment_group_id` is not null requires an `EditScope`:

| Scope | Affects |
|---|---|
| `THIS` | Only the selected row. |
| `THIS_AND_FOLLOWING` | The selected row and every row with a higher `installment_number`. |
| `ALL` | The whole series. |

- `payment_method`, `card_id`, `account_id`, `currency`, `installment_total` and `transaction_date` can only be changed with scope `ALL`. Such a change **regenerates** the series using the rules in §10.1–§10.3. With scope `ALL`, `amount` is read as the **new total**.
- With `THIS` or `THIS_AND_FOLLOWING`, `amount` is the new per-row amount, and the series total changes to match.
- Deleting a row on its own does not renumber the remaining rows.
- When a split purchase is edited or deleted, only the targeted part's amounts and payment details change. Purchase-level fields (`transaction_date`, the person, `currency`, `category_id`, `description`) are kept identical on every part, so changing them on one part changes them on all (§10.5).

### 11.1 Income rules

- **Payment date:**
  - For `CASH`, `PIX`, `DEBIT`, `BOLETO` and `BANK_TRANSFER`, the payment date is `transaction_date`, with no adjustment.
  - For `CREDIT` (for example, a sale on a card machine), the payment date is the **same day of the next month** (`transaction_date + 1 month`, clamped), then moved to the next business day if needed (§17).
- **Installments:** N consecutive monthly rows from the anchor. Amounts are split and rounded the same way as for expenses (§10.1). Each credit installment date gets its own business-day adjustment.
- **Split payments and editing scopes:** identical to Expense (§10.5–§10.6).

## 12. Recurrence (fixed entries)

A Recurrence is a **fixed expense or income** (rent, salary, subscriptions) that repeats while it is valid. It is a **template**:

- It does not create rows automatically.
- Its future occurrences always count in projections (§13).
- When an occurrence actually happens, the user **registers** it, which creates a real Expense or Income row linked to the Recurrence.

| Field | Type | Req. | Default | Constraints / notes |
|---|---|---|---|---|
| `id` | uuid | Yes | auto | |
| `household_id` | uuid → Household | Yes | | |
| `type` | EntryType | Yes | | `EXPENSE` or `INCOME`. Cannot be changed after creation. |
| `person_id` | uuid → User | Yes | current user | The spender for expenses or the receiver for incomes. |
| `amount` | decimal(12,2) | Yes | | Greater than 0. The **expected** amount of each occurrence. |
| `currency` | Currency | Yes | household `default_currency` | |
| `payment_method` | PaymentMethod | Yes | | |
| `card_id` | uuid → Card | Cond. | | Only for `EXPENSE`. Same rules as `Expense.card_id`. |
| `account_id` | uuid → Account | Yes | | Same rules as `account_id` on Expense or Income. For card methods, the card's account is used. |
| `category_id` | uuid → Category | Yes | | Must be active, with a `type` that matches the Recurrence. |
| `description` | string(≤200) | No | | |
| `interval_months` | integer(1–12) | Yes | `1` | 1 means monthly, 12 means yearly. |
| `day_of_month` | integer(1–31) | Yes | `start_date.day` | For credit card expenses, always the card's `due_day` (§12.1). |
| `start_date` | date | Yes | today | First possible occurrence. |
| `end_date` | date | No | | Last possible occurrence. Null means no end. Must be on or after `start_date`. |
| `skipped_dates` | date[] | No | `[]` | Occurrences that the user said will not happen (for example, a month without the gym). |
| `is_active` | boolean | Yes | `true` | `false` pauses the Recurrence, removing it from projections without deleting it. |
| `created_by_id` | uuid → User | Yes | current user | |
| `created_at` | timestamp | Yes | auto | |
| `updated_at` | timestamp | Yes | auto | |

### 12.1 Occurrences

- **Occurrence dates:** day `day_of_month` (clamped) of every `interval_months`-th month, counting from the month of `start_date`. Dates before `start_date` or after `end_date` are dropped.
- An occurrence is **valid** when the Recurrence `is_active`, its date is within [`start_date`, `end_date`], and its date is not in `skipped_dates`.
- An occurrence is **registered** when an Expense or Income row exists with the same `recurrence_id` and `occurrence_date`. Each occurrence can be registered **at most once**.
- An occurrence is **pending** when it is valid, unregistered, and its date falls in the current month.
- An occurrence is **overdue** when it is valid, unregistered, and its date is in an earlier month. Overdue occurrences are **never registered automatically**. They stay overdue until a user registers or skips them.
- **Payment date of an occurrence:** computed with the payment-date rules for its method (§10.2, §10.3 and §11.1), using `occurrence_date` as the `transaction_date`.
- **Credit card fixed expenses** (`type = EXPENSE`, `payment_method = CREDIT`) run on the card's bills: each occurrence **is a statement's due date**.
  - `day_of_month` is always the card's `due_day`. The server sets it on create and update, ignoring the client's value. When a card's `due_day` changes, its credit recurrences follow: `day_of_month` changes, and registered rows and `skipped_dates` move to the new day in the same month.
  - The payment date of an occurrence is the occurrence date moved to the next business day (§17).
  - When an occurrence is registered without a `transaction_date`, the row gets a purchase date inside that statement (§10.3), so it is paid with that bill. The date is today while the statement is still open, otherwise the statement's nearest day (its first day if it hasn't opened yet, its last day if it has closed).

### 12.2 Registering an occurrence

- Registering creates a normal Expense or Income row, pre-filled from the Recurrence and with `recurrence_id` and `occurrence_date` set.
- Every field can be edited before saving, because the actual amount can differ from the expected one (for example, an electricity bill).
- Overdue occurrences can be registered the same way.

### 12.3 Changing a recurrence

- Editing a Recurrence affects **only unregistered occurrences**. Registered rows are never modified.
- To change the amount from a given date onward while keeping history accurate, the user ends the current Recurrence (`end_date`) and creates a new one. The UI offers this as a single action (see §8 of `be-rich-ui/specs/ui-behavior.md` in the UI repository).
- Deleting a Recurrence that has registered rows asks what happens to them: they are deleted too, or kept as regular entries, unlinked from it (§18).
- Ending a Recurrence never drops a registered occurrence: if one is later than the chosen `end_date`, the end moves to it.

## 13. Projections

A **projection** answers the question "what will happen between dates X and Y?". It is used for future expenses, future incomes and projected balances.

### 13.1 What a projection includes

For a period [`from`, `to`], every item is placed by its **payment date**. A projection includes:

1. **Stored rows:** every Expense and Income row with `payment_date` in the period. This includes future installments, which already exist as rows.
2. **Projected occurrences:** every **valid, unregistered, non-overdue** Recurrence occurrence (meaning pending or future) whose payment date is in the period. Their amount is `Recurrence.amount`, and they are marked `projected: true`.
   - A pending occurrence whose computed payment date has already passed is placed on **today**, because the money is still expected to move.
   - Overdue occurrences are **excluded** from projections. They are reported separately (§12.1) so they can't silently distort future numbers.

### 13.2 Actuals versus projections

- **Actuals** (reports on past periods) include only stored rows.
- **Projections** include stored rows and projected occurrences.
- A period that spans today, such as the current month, is shown as a projection, with each item marked actual or projected.

### 13.3 Net result

The **net result** of a period = Σ incomes − Σ expenses, converted to `default_currency` (§16).

## 14. Account balances

### 14.1 Balance of an account on a date

For an account `a` on a date `t` (at end of day):

```
balance(a, t) = opening_balance(a)
              + Σ income amounts  with account_id = a and opening_balance_date < payment_date ≤ t
              − Σ expense amounts with account_id = a and opening_balance_date < payment_date ≤ t
```

- **Current balance:** `t = today`, counting only stored rows.
- **Projected balance:** `t > today`. It is the current balance plus every item from the projection (§13.1) with an account of `a` and a payment date in (today, `t`]. Projected occurrences use the Recurrence's `account_id`.
- **Currencies:** a row whose currency differs from the account's currency is converted into the account's currency (§16.3).
- **Dates before the opening:** a `t` earlier than `opening_balance_date` has no defined balance. The API returns null.

### 14.2 Household balance

- **Total balance** = Σ `balance(a, t)` over every account (including archived ones), each converted to `default_currency`.
- **Cumulative projected balance:** the total balance at the end of each month, from the current month onward. This is the main line of the projection chart.

### 14.3 Reconciliation

- A user can **adjust** an account to match the real bank balance. This sets `opening_balance` to the value they enter and `opening_balance_date` to the chosen date (default today).
- Earlier rows stay stored for reports, but they no longer affect the balance (§7).

### 14.4 Credit cards

A credit purchase affects the paying account on its `payment_date` (the statement's due date), **not** on the purchase date. The account balance therefore reflects when the money actually leaves.

## 15. Totals and aggregation

- Every sum is computed in the household's `default_currency`.
- Each amount is converted at full precision, the converted amounts are summed, and the **final** result is rounded to cents.
- Every API response that contains converted totals also returns `currency` and `rates_as_of` (the date of the oldest rate used), so the UI can disclose them.

## 16. Currency conversion and ExchangeRate

**Principles:**

- Every row keeps its **original** `amount` and `currency`. Converted values are never stored on rows.
- Rates are fetched **by the server**, never by the browser. This keeps them consistent for every member, avoids per-user rate limits and CORS problems, and keeps any API key secret.

### 16.1 ExchangeRate (system-wide cache)

| Field | Type | Req. | Constraints / notes |
|---|---|---|---|
| `id` | uuid | Yes | |
| `rate_date` | date | Yes | The date the rate refers to. |
| `base` | Currency | Yes | |
| `quote` | Currency | Yes | |
| `rate` | decimal(18,8) | Yes | 1 `base` = `rate` × `quote`. |
| `source` | string(≤40) | Yes | Provider identifier. |
| `fetched_at` | timestamp | Yes | |

(`rate_date`, `base`, `quote`) is **unique**.

### 16.2 Fetching rates

- A scheduled job fetches the latest rates for every supported `Currency` **once a day**.
- Missing **historical** rates are fetched on demand and then cached permanently, since past rates never change.
- **Provider:** a free provider that needs no API key and supports BRL and historical rates, such as **Frankfurter** (European Central Bank reference rates). **AwesomeAPI** (Brazilian) is an alternative. The provider sits behind an interface so it can be swapped.

### 16.3 Which rate is used

| Item | Rate |
|---|---|
| A stored row with `payment_date` ≤ today | The rate on its `payment_date`. If that day has no rate (weekends and holidays), the most recent earlier rate. |
| A stored row with a future `payment_date`, or a projected occurrence | The latest available rate. |
| An account's `opening_balance`, when included in household totals | The latest available rate. A balance is a current value, not a historical one. |

Using historical rates for past rows means past reports don't change every time the rate moves.

### 16.4 Failures

- If the provider is unavailable, the most recent cached rate is used and `rates_as_of` reports how old it is.
- If no rate has ever been cached for a currency, amounts in that currency are left out of the total and returned separately as `unconverted: [{currency, amount}]`, so the UI can show a warning.

## 17. Business days and Holiday

A **business day** is a Monday to Friday that is not a bank holiday.

**When an adjusted date is not a business day, it moves forward** to the next business day. This applies to:

- `CREDIT` expense payment dates (card due dates, §10.3);
- `CREDIT` income payment dates (§11.1);
- projected occurrences of `CREDIT` recurrences.

It does **not** apply to the other payment methods, because their payment date is the date the user actually paid or received.

### 17.1 Holiday (system-wide)

| Field | Type | Req. | Constraints / notes |
|---|---|---|---|
| `date` | date | Yes | Primary key. |
| `name` | string(≤60) | Yes | |

- **Contents:** **national bank holidays**, meaning the national holidays plus the days banks close nationwide (for example Carnival Monday and Tuesday, Good Friday and Corpus Christi). Verify the list against the FEBRABAN calendar.
- **Source:** holidays are generated per year (fixed dates plus Easter-based dates), or imported from a public source such as BrasilAPI. The table is filled at least 2 years ahead.
- Municipal and state holidays are out of scope.

## 18. Integrity and lifecycle

- **Archiving instead of deleting:** a Card, Account or Category that is referenced by any Expense, Income or Recurrence **cannot be hard-deleted**. It can only be archived (`is_active = false`). Archived records:
  - are rejected when creating new records;
  - are kept on, and still displayed with, existing records;
  - can be reactivated.
- **Archived accounts keep their balance**, which still counts in the household total (§14.2).
- **The last active `CASH` account** cannot be archived.
- **Archived cards, accounts and categories in recurrences:** a Recurrence that uses one of these still projects. However, its occurrence cannot be registered until the reference is replaced or reactivated, and the UI flags it.
- **Users are never deleted** as part of household operations. Leaving or being removed moves them to their own household (§4.2).
- **Recurrences:** a Recurrence can be hard-deleted. Its registered rows are either deleted with it or kept as regular rows (`recurrence_id` and `occurrence_date` set to null); the caller chooses (api.md §12). It can also be ended (`end_date`) or paused (`is_active = false`).
- **Expenses and incomes** are hard-deleted, following the scope rules in §10.6. Deleting a row registered from a Recurrence turns that occurrence back into unregistered.
- **Household isolation:** every query is scoped to the caller's current household. New cross-household references are rejected.

## 19. Out of scope for v1

- **Moving an existing account to another household** through an invitation. This also means a former member cannot be invited back (§6.1 rule 6).
- Municipal and state holidays (§17).
- Automatically registering overdue fixed entries (§12.1). This was a deliberate decision.
